The full run was always going to take a long time. For a while it went fine. The last count in my notes was about 640 finished runs out of 1,638, with no failures.

Then I closed the wrong window. Jupyter runs inside a command prompt window on my laptop, and I closed that window without thinking about what was in it. The experiment stopped. Right after that I was away for a few days. While I was gone I got some advice about it that I followed without really checking, so when I came back I really didn't know whether anything in the project had been changed or deleted.

I didn't start anything. The runner was built to skip finished runs and continue, so in theory one command would pick up from run 641. But if the files were damaged, running it could overwrite whatever was still good. So the first thing I did was copy the results folder, the source code and the splits file somewhere safe. Only after that did I start checking.

Some of it was good news. The splits file was exactly as I had left it, with the same date and contents it had when I froze it. Every file in src had a last-changed date from before I left, and the two bug fixes from a few days earlier were still in the code.

The results were not. The CSV that should have had about 640 rows had 2. There was one saved model where there should have been hundreds. I looked for anything else that might still have a copy: the backup I had just made, the automatic copy Jupyter keeps, and the Windows recycle bin. The first two were identical to the 2-row file, down to the same size and timestamp. The recycle bin had nothing from the project. Whatever happened, the file had been overwritten by a program rather than deleted by hand, so there was nothing to recover.

I also can't fully explain the number 640. Either the run really got that far and the file was overwritten later, or the number in my notes was wrong from the start. The evidence on disk can't tell me which one it is.

The checking turned up one more uncomfortable thing. My notes said two analysis scripts were already written and ready. Neither one existed on my laptop. They had been written somewhere else and never saved into the project. I had been trusting a list of things that sounded finished.

Before starting again, I set up git, which I should have done from the start. The first commit saved all of the source code, and the second one saved the splits file. If anything changes from now on, I'll be able to see exactly what changed and when, and go back if I need to.

Then I tried to delete the broken 2-row file and got a permission error. The reason was that I had it open in Excel. After closing Excel I deleted it and started the full run again from zero, split into three stages so that the quickest overview results would come in first.

The rerun didn't cost me anything scientifically. Because the splits are frozen, it uses exactly the same people in exactly the same groups, so its results are directly comparable to whatever the first run would have produced. What I lost was time, about two days of GPU work. What I took from it is two rules I'm keeping for the rest of the project: every result gets written to disk the moment it exists, and if my notes say something is done, I check the disk before I believe it.
